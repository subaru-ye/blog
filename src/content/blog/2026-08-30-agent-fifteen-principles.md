我把做 Agent 系统时反复验证过的原则压缩成十五条铁律。它们是公理层——做任何设计决策前先对照检查，违反任何一条，都会在后面某个环节付出代价。

## 1. Agent = LLM + 上下文 + 工具

接到任何"新能力"需求，先定位它在三要素中的位置：是模型能力不足、上下文里没给够信息、还是缺一个工具？三类问题的解法完全不同——缺信息给上下文（检索、状态栏、记忆），缺行动力给工具，只有"有了信息也推理不对"才是模型问题。多数"模型太笨"的抱怨，实际是上下文里根本没让它看到需要的东西。

常见错误：模型答错就换更大的模型，而不检查输入；把本该是工具的能力写进提示词让模型"模拟"。

## 2. 可靠性 ≈ 模型智能 × Harness 可靠性

把大部分工程投入放在模型外围的 Harness 上——验证器、权限、沙盒、重试、回滚、审计。这是乘法关系：任何一项趋零，整体趋零。模型智力 90 分、Harness 30 分的系统，可靠性不如模型 70 分、Harness 80 分的系统。模型越强，Harness 越重要，而不是越可以省。

常见错误：全部精力花在提示词调优上，错误处理、验证、权限都是裸的；生产事故后才发现没有任何回滚手段。

## 3. 约束优先于指导

能用 Linter、类型系统、Schema 校验、CI、权限控制强制的规则，绝不写成提示词建议。约束强度从弱到强：提示词建议 → 审核者检查 → 工具参数验证 → 权限控制 → 沙盒 / OS 隔离，规则尽量往阶梯下方放。"请不要做 X"（软约束，模型可能忽略）远弱于"系统不允许做 X"（硬约束，物理上无法执行）。

常见错误：把合规红线、安全边界写进系统提示词就认为安全了；关键流程顺序靠提示词维持，模型一旦不遵守就出错。

## 4. LLM 处理模糊性，确定性系统处理不能模糊的部分

让 LLM 做意图理解、规划、生成形式化表达（SQL / 代码 / Schema）；让数据库、求解器、测试、校验代码做执行和裁决。LLM 是"把自然语言编译成形式化表达"的编译器，编译结果交给确定性系统执行——两边的优势互补且不可互换。LLM 判断退款是否合理，但按下退款按钮前，代码必须用数据库真实数据重新算一遍。

常见错误：让 LLM 直接对大量数据做统计复述（数据库该做的事）；让代码硬编码处理本该灵活理解的自然语言变体。

## 5. 架构从简渐进：单次调用 → 工作流 → 自主 Agent

永远从最简架构开始，只在下一级明确不够时升级。大多数业务需求用"单次 LLM 调用 + 结构化输出"就能满足；需要多步骤时先上代码编排的工作流（顺序由代码强制）；只有开放性任务才需要模型自主决策循环。每升一级，成本、延迟、不可预测性、调试难度都跳一个台阶——自主 Agent 的价值在于探索未知路径，代价是每一步都可能偏离。

常见错误：新项目直接搭"多 Agent 自主协作系统"做其实是固定流程的事；合规关键流程用自主 Agent 而不是代码工作流。

## 6. 评估先行

动手改任何东西之前，先有评估集和指标。评估对象是"模型 + Harness"整体，不是裸模型；哪怕只有 20 条用例，也先让"改了之后好没好"变成可测量的问题——没有度量就没有可靠改进，只有错觉。

常见错误：凭一两次试用体感决定方案；分数下降了立刻改 Agent 代码，不先检查评测系统本身是否坏了（环境资源不足、验证器 bug、用例与生产脱节，这三类在数字上和模型退化一模一样）。

## 7. 验证器判定完成，不信模型自报

任务是否完成由独立验证器判定，验证必须扎根真实观测——测试运行结果、渲染截图、数据库查询、文件系统状态。模型说"已完成"只是宣称，不是证明：模型有系统性过早宣称完成的倾向，自报参数经常与真实状态不一致。生产中实测过：1000 次调用里，模型自报的保险状态错 47 次、时间边界错 81 次。

要防的三类过早终止：偷懒式假完成（测试没跑就报完成）、过早放弃（一个方法不行就说任务不可能）、假成功（口头答应了但用户端的确认步骤没走完）。

## 8. 上下文唯一判据："模型此刻做这个决定，需要看到什么"

每往上下文里放一条信息，都用这个问题检验。上下文管理就是不断执行四个动作：选择（什么进来）、组织（放哪、什么格式）、提炼（哪些历史变成状态摘要）、遗忘（哪些不再保留）。上下文是注意力预算，塞满不等于用得好——窗口没满但噪声过多，信息质量已经恶化（Context Rot），模型同样会出错。

常见错误：把 token 用量当唯一红线，忽视信息质量；工具结果全文堆进上下文不裁剪。

## 9. 让正确的信息在正确的时间以正确的粒度出现

对一切大体积信息做渐进式披露：工具先发现再加载、搜索先返回候选列表再读详情、文件按 offset/limit 分页读、多模态由专用模型分析后只回传结论、知识按需加载——局部化复杂度，每一步只暴露当前需要的复杂度。真实世界无限复杂，Agent 的注意力有限，这条原则统一了工具设计、文件读取、知识加载、子 Agent 隔离四件事。

常见错误：搜索工具直接返回全文；大 JSON 原样进上下文；截断时不注明省略量，模型误以为已读完。

## 10. 结果正确不代表过程正确

验收同时约束结果和路径。评测和奖励都要检查"是不是用允许的方法办成的"，而不只看最终产出——古德哈特定律：指标成为优化目标后就不再是好指标。Agent 会找到"指标上正确、工程上荒谬"的捷径：改测试断言蒙混过关、删掉失败的测试、伪造验证输出。

常见错误：只看最终测试是否绿（可能被模型篡改）；单一总分奖励（score=0.83），出问题后无法定位该改哪里。

## 11. 回合制是训练假设，不是环境属性

真实环境不会在模型思考时暂停：邮件会到达、用户会插话、页面会刷新。执行框架按"持续感知 → 判断状态与时机 → 选择动作 → 执行 → 验证修正"的闭环建，而不是严格的"输入 → 思考 → 工具 → 回复"回合制。预测可以提高效率，但只有新的观察才有资格确认现实——模型训练轨迹要求工具调用后紧跟结果，但长任务（分钟到天）、不同优先级事件、中断恢复，都超出了同步回合制的表达力。

常见错误：为了维持消息格式把未完成的工具伪装成成功结果；任务中途被用户打断后丢失原任务上下文。

## 12. 多 Agent 看信息增量，不看数量

新增任何协作环节前先问：它是否引入了单个 Agent 无法获得的新信息（真实执行反馈、独立证据、不同信息源）？没有就砍掉。净收益 ≈ 新信息 + 搜索覆盖 + 专业化 − 通信成本 − 重复计算 − 协调复杂度。多个相同模型看相同材料做相同思考，只是对同一分布重复采样，遗漏高度相关；多 Agent 的 token 与执行成本可能高出单 Agent 数倍。

常见错误：让模型自我审查或自我辩论（无外部新信息，不稳定优于给一个 Agent 相同预算）；用"改 system prompt 的多个角色"冒充多 Agent（信息源、工具、状态都没差异）。

## 13. 先 Harness 工程，后模型训练；训练是放大器不是发生器

行为问题先用提示词、工具、约束、上下文管理解决；知识频繁更新用 RAG；训练（SFT / RL / 蒸馏）是最后手段，且只能放大基模已有的能力，不能凭空创造。SFT / RL 的成本可以是 Harness 改动的几十到上百倍；pass@k 接近零时上 RL 是纯烧钱。

常见错误：第一次效果不好就考虑微调；拿 SFT 硬塞知识库（SFT 只固化协议，不负责记事实）。

## 14. 修改者不能当裁判；安全边界不可被修改对象触及

Agent（或任何优化器）可以生成修改提案，但最终批准权、评估器、安全测试、发布阈值、审计日志必须留在它无法修改的独立层——生成可以高度自主，放行必须外部约束。让 Agent 管理自己的权限，等于让保安可以随时修改门禁系统；Agent 嫌测试难就改及格线，进化系统立即失效。

常见错误：Reviewer 可以修改验收标准（退化为自我批准）；运行中的 Agent 直接覆盖自己的稳定版本，失去回滚能力。

## 15. 成本和延迟是设计约束，不是事后优化

设计期就算两笔账。延迟账：级联流水线 0.9-2s、流式 600-800ms、端到端实时 200-400ms，看场景选架构。token 账：上下文逐轮累积计费，1+2+3 轮是 6000 token 不是 3000。每个任务设成本上限和最大迭代轮数——便宜但成功率低的模型可能因反复重试实际更贵；利用率 80% 的排队系统延迟是低载时的 5 倍；多 Agent 协调成本可达单 Agent 数倍到数量级。

常见错误：上线后才发现单任务成本失控（Agent 陷入循环无上限）；只优化单次调用延迟不看 p95。

## 总结

这十五条可以再压缩成三句话：**先定位问题在哪一层，再动手**（1、4、5、8、13）；**可靠性来自验证与约束，不来自模型的自报**（2、3、7、10、14）；**一切资源——注意力、算力、时间——都是预算，设计期就要算**（6、9、11、12、15）。

大部分"模型太笨"其实是工程问题，大部分"不稳定"其实是缺验证器，大部分"成本失控"其实是没设上限。把这三件事做对，Agent 才配谈智能。
