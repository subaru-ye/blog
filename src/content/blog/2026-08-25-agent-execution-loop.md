Agent 主循环（ReAct 循环）是整个系统的心脏。生产级 Harness 必须回答四问：**什么算完成（验收基线）？什么允许做（执行边界）？做错了吗（反馈信号）？出错怎么办（回滚）？**下面按循环控制、错误恢复、安全兜底、事件驱动、异步接续五块展开。

## 循环控制与完成判定

### 主循环必须有明确停止条件

主循环设最大迭代轮数、每任务 token / 成本上限、连续失败升级人工的阈值，每轮开始前检查这些全局限制。模型没有天然的"停下来"能力，没有硬上限的循环在遇到困难任务时会无限烧钱。

反模式：只依赖模型自己决定何时结束；全局预算只在会话层设置，单任务可以绕过。

### 无进展检测：调用指纹

对每次工具调用计算指纹 `hash(tool_name + parameters)`，连续 N 次相同指纹即判定无进展循环，触发干预：改变搜索策略、强制反思、或终止该恢复路径。模型卡住时的典型表现是机械重复完全相同的调用，这类循环自己不会收敛。

只检测"连续失败"是不够的——要检测的是"连续**相同的**失败"，后者才是死循环信号。

### 完成判定：验证器说了算

完成标准定义为"验收测试通过"，而非"代码写完"、"模型说完成"。验证器扎根真实观测：跑测试、渲染页面截图、查数据库终态、读文件系统。复杂任务先写设计文档供人审查再动工——审一页文档比审几百行代码容易得多。

模型在缺乏证据时下结论是系统性倾向，三类过早终止（假完成 / 过早放弃 / 假成功）都必须由外部验证拦住。完成信号来自模型消息里的"已完成"字样、验证器只查"输出存在"不查"输出正确"，都是裸奔。

## 错误分类与恢复

### 错误先分类，再选恢复策略

失败当正常状态设计，维护"错误类型 → 恢复策略"映射：

- **API 层**：429 / 超时 / 截断
- **工具层**：不存在 / 参数非法 / 执行异常 / 重复失败
- **上下文层**：溢出 / 压缩失败 / 调用与结果不配对
- **控制流层**：死循环 / 恢复自身再失败

恢复分级：**静默重试（可重试错误，带上限）→ 降级（换工具 / 换路径）→ 暴露用户（带上下文求助）**。"出错就重试"的统一策略很危险：429 可以重试，非法参数和权限不足必须改策略——重试只会重复失败。恢复动作本身也要有失败处理。

### 每条恢复路径设独立熔断上限

某条恢复路径连续失败达阈值即熔断，转入其他路径或人工处理；每条路径的上限独立计数，且有全局兜底（最大迭代、单任务成本、连续失败升级人工）。恢复机制自己失败是常见的失控来源，无上限的恢复就是死循环的高级形态。只有全局熔断没有按路径熔断时，换路径后又从头计数，总量仍无界。

### 结构化错误回喂，让模型自纠

错误信息用结构化格式返回给模型：错误类别、原因、约束、可修正的建议。写文件后自动跑 linter，把 linter 输出直接作为下一轮输入——**错误不是终点，而是下一轮推理的观察结果。**模型有"调用 → 失败 → 读错误 → 调整"的既有能力，结构化错误让这个能力可用；纯字符串堆砌的错误让模型只能瞎猜。吞掉错误只返回 false，是把这个能力直接焊死。

## 安全兜底：三层保障

安全关键规则分三层落地：

1. **自然语言策略**——帮模型理解规则，不能兜底
2. **工具 Schema / Checklist**——强迫调用前核对、暴露判断依据，不能兜底
3. **服务端确定性校验**——数据库真实数据 + 服务器真实时间 + 硬编码规则，**唯一能承担最终安全责任的层**

Checklist 提高"Agent 别判断错"的质量，Guardrail 保证"即使判断错了也不能错误执行"——两回事，都要有，但只有后者兜底。模型自报参数与真值不一致是实测过的：1000 次调用中保险状态错 47 次、时间边界错 81 次，Reasoning Checklist 里模型自报"已核对"不能作为真值。

还有一条边界要分清：允许 Agent 生成规则 ≠ 允许 Agent 自行让规则获得生产权限——后者禁止；最终守门必须基于模型输出之外的独立数据源。

## 事件驱动架构

### 统一事件模型：一切输入都是事件

把用户消息、定时器、工具结果、Webhook、系统告警统一为结构化事件入队，由事件循环驱动 Agent。事件至少含：来源、类型、优先级、关联任务、载荷、时间；生产系统再加事件 ID、幂等键、权限边界。队列里事件多时逐条编号 + 末尾汇总未处理项，否则模型只关注最后一条。

事件模型天然区分"用户指令 / 工具结果 / 不可信外部内容"，降低角色混淆和注入风险。队列最危险的问题不是"没收到"，而是"重复收到、乱序到达、处理一半崩溃"——幂等、重试、持久化、审计与 LLM 判断同等重要。另外别用轮询冒充事件驱动：定时轮询只能产生"主动的外观"，实时外部事件需要 Webhook / Channel（配鉴权、重试、去重）。

### 事件按紧急度分三路处理

新事件到达时三选一：

- **取消式**：紧急且冲突（"停！别发邮件"）——在安全点停止当前步骤，注入事件重规划
- **队列式**：相关但不紧急（"报告改用中文"）——等当前步骤完成，批量交给模型
- **并行式**：独立且轻量（长任务中问天气）——新开会话处理，结果写回主轨迹

全部排队会饿死紧急事件，全部打断会破坏任务连续性。取消必须发生在**安全点**（一段推理结束、一次工具返回、一个动作块结束），在任意指令中间强行取消是事故之源。

## 异步与中断恢复

### 异步工具契约：启动与完成分离

耗时工具（分钟级以上）拆成"启动"和"完成"两个阶段：`initiate_phone_call()` 立即返回 `task_id`，后续以 `phone_call.connected` / `phone_call.ended` 事件流交付结果。训练格式要求 tool call 与 tool result 对应，异步场景下用任务 ID 维持对应关系，而不是伪造结果维持格式相邻。

消息纪律：工具调用先记 assistant 消息，真实结果完成后再记 tool 消息；中途打断则写入明确的"未完成 / 已取消"占位结果；模型推理被打断则丢弃半截输出，防污染轨迹。把未完成的工具伪装成成功结果是重罪。

### 输出中断后的接续

模型输出被截断（思考中途 / 正文中途 / 工具参数中途）时二选一：整轮重发，或以半截输出为前缀续写。续写的关键：半截的工具调用先转成文字再补完，拼接后重新解析校验；流式阶段已提前执行的工具按调用指纹去重，防止重复副作用。直接把半截 JSON 当有效调用解析、续写后不校验格式，都会埋雷。

### 有状态工具按运行时管理

Shell、浏览器会话等本质是**有状态运行时**，不是无状态 RPC。Agent Runtime 要管理工具生命周期（创建、复用、超时、回收）、并发工具调度、错误传播、状态快照与恢复。把 Shell 当无状态函数，会丢失工作目录、环境变量、后台进程等隐式状态，产生"上一步明明成功了"的诡异失败——每次调用起新 Shell 却依赖之前 cd 的目录、并发调用共享同一 Shell 导致输出串流，都是这个错误的具体形态。

### 结果与路径双重约束

验收同时检查最终产出和达成路径。可以形式化为"结构 + 操作 + 验证"的任务，把路径约束写成机器可查的规则：不许改测试断言、完成声明必须附带真实执行过的命令输出、不许为通过校验而删校验。Agent 会找到"指标上正确、工程上荒谬"的捷径——hack 验证环境、mock 掉被测逻辑、为过 lint 而删 lint。只看测试绿不查测试是否被改过、完成声明与真实执行历史不交叉核对，都等于没验。

## 总结

执行循环设计的核心是把四问工程化：**停止条件是上限不是自觉，完成判定是验证不是自报，错误恢复是分级的地图不是一把 retry，安全兜底在服务端不在提示词。**把模型当成一个聪明但会偷懒、会嘴硬、会犯相同错误的执行者去设计外围，循环才能从"能跑"变成"敢上生产"。
