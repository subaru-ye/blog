上下文工程是单次会话内的信息治理。判断一切的标准只有一句话：**模型此刻做这个决定，需要看到什么。**上下文是注意力预算——塞满不等于用得好，窗口没满但噪声过多，模型同样会出错。下面按格式、组织、压缩、隔离、工程化五个层面整理我在实践中沉淀的规则。

## 格式与缓存

### 五组件与严格的角色格式

上下文完整包含五组件：系统提示词、工具定义、用户消息、模型回复（含 reasoning）、工具结果。消息严格使用标准角色格式（system / user / assistant / tool），工具结果以 `tool` 角色回传，reasoning 按厂商文档要求回传。

消息列表会被 Chat Template 转换成模型训练时的线性序列，格式不对等于让模型看到训练时没见过的模式；工具结果角色错误会破坏模型对"我说了什么 / 环境答了什么"的区分。

反模式：把工具结果拼成 `USER:` 文本自己模拟格式（破坏 KV Cache 且可能触发模板清理逻辑）；丢掉 reasoning 不回传（模型丢失自己之前的思考过程）。

### KV Cache 一致性：静态前缀冻结，动态信息尾部追加

把 Prompt Cache 一致性当前置架构约束：系统提示词和工具定义定稿后一个字符都不改；所有动态信息（时间戳、用户状态、会话数据）一律作为新消息追加到上下文末尾；缓存边界前不放任何运行时条件；子 Agent 前缀与父 Agent 字节级对齐。

前缀改一个字符缓存即全废。前缀嵌入当前时间戳，会让首 token 延迟从 0.5s 涨到 3-5s、月度推理账单近翻倍；缓存读取成本约为首次计算的 1/10。N 个二值运行时条件放在缓存边界前，会产生 2^N 种缓存键变体，直接摧毁命中率。

反模式：动态系统提示词；前缀嵌用户配置；工具定义按使用频率动态排序；滑动窗口裁剪对话历史（Agent 忘记工具结果陷入重复调用）。另外部分厂商需显式设置缓存断点（有最小 token 数和 TTL 限制），并非自动命中。

## 组织与状态

### 系统提示词用流程驱动 SOP，不平铺规则

把多阶段任务写成状态机式流程，每个阶段写明触发条件、动作、退出条件；规则组织成带语义标签的层级结构。例如文件处理 SOP：

```text
阶段 1 Validation     → 检查文件是否存在，不存在则停止
阶段 2 Classification → 判断文件类型
阶段 3 Preprocessing  → 配置文件先备份；大文件流式读取
阶段 4 Execution      → 执行操作
阶段 5 Verification   → 验证处理结果
```

平铺 100 条业务规则，模型每次推理都要自行推断适用性、优先级、当前阶段，极大消耗推理能力；SOP 把"现在该做什么"变成确定性的。

### 状态栏：隐式状态显式化，用代码维护

把任务执行中模型需要持续感知但会随轮次漂移的状态——当前分支、已完成步骤、测试状态、剩余任务、当前时间——由**确定性代码**在每轮推理前注入上下文（通常放末尾），并配上操作策略（如"状态栏显示测试失败时，先修复测试再继续新任务"）。内容分三类：任务状态、环境状态、执行统计与异常。

注意力机制擅长检索已存在的信息，但不会自动把散落在历史里的信息持续归纳成状态；让 LLM 自己"猜"系统状态，会引入幻觉式状态。

反模式：状态栏内容由模型生成而非代码维护；只给状态不给对应操作策略。

## 压缩与分层

### 批量压缩与显式的保留优先级

上下文接近窗口阈值（如 80%）时批量压缩，而不是每轮零碎删。压缩必须任务感知——压缩器知道三个问题的答案才算合格：用户要解决什么、已经掌握什么、下一步还缺什么。显式定义保留优先级：**标识符（hash / URL / 文件名）、决策理由、TODO、验证状态必须保留**；语义内容可有损压缩，但来源索引尽量无损保留。

无任务感知的压缩会把任务相关信息当噪声删掉；来源信息丢失后无法回查，模型开始编造引用。压缩后丢失"为什么这么做"的决策记录，模型会重复探索已否决的路径。

### 上下文四层分层与信息生命周期

把上下文当操作系统内存管理：

1. 长期稳定规则（很少变）
2. 当前任务需要的专业知识（Skills 按需加载）
3. 原始工作记忆（对话轨迹，压缩）
4. 提炼后的工作状态（状态栏，持续更新）

每条信息问三个问题：从什么时候开始有用？要活多久？什么时候可以丢？不同信息的生命周期完全不同——长期规则频繁变动会破坏缓存；临时工具输出久留会污染注意力。把所有信息当同等数据同等处理，是上下文腐烂的起点。

## 隔离与渐进披露

### 子 Agent 隔离：高噪声探索只回传摘要

大量读取、搜索、试错的高噪声探索委派给子 Agent（或独立会话），它只把结构化结论回传主上下文；给子 Agent 的任务描述必须自包含：角色、信息来源、任务边界、输出格式。主上下文的注意力预算留给决策，不留给原始数据——这是"最好的压缩是不让信息进来"的实现方式。

### 长输出与文件读取的上下文经济

工具返回长输出（npm install、docker build、日志）时保留头尾各约 50 行 + 中间标注 `[省略 N 行]`，完整内容落盘到文件供按需读取——头部是初始化信息，尾部通常是最终错误。`read_file` 必须支持 offset/limit 并明示当前范围与总行数。

最忌静默截断：模型会产生"已读完"的错误认知；一次性把 100K 字符的搜索结果塞进上下文同理。

### Skills 渐进披露与成本核算

操作知识写成独立文档（Skill），用到时才加载进上下文，用完退出，Skill 正文以 user 消息注入。它把"专门的机器检索问题"重新表示成模型擅长的"阅读文档问题"，复用已有的文件系统 + 搜索 + 阅读能力。注意成本差异：用户显式调用（斜杠命令）由客户端本地展开，无额外往返；模型自主发现要先调用一次"启动 Skill"工具再加载正文，**多一次 LLM 往返**——算成本时别漏算这条路径。

## 工程化

### 轨迹按中立格式存储

会话轨迹不要按任何单一厂商的接口格式存。思考内容拆成"可移植文字"和"不可移植凭证"（reasoning token 是厂商私有签名，跨厂必失效）；工具调用只记录名称与参数，标识符在渲染时按目标厂商动态生成。任务中途切厂商（限流、故障）时，直传原格式会被严格校验的厂商拒收；一刀切删除所有思考，在宽松端可用、严格端反而验证失败。

反模式：把厂商专属的 reasoning 凭证存进数据库当唯一事实；切换后未处理的半截工具调用被当成真实调用重放。

### 提示词是代码：确定性渲染 + 版本化 + 回归

系统提示词能确定性渲染（相同输入永远产生相同文本，含条件展开后的最终结果）；建立版本快照机制（能从任意版本提取完整渲染后的提示词）；每次变更都在评估集上跑回归，如同代码变更跑 CI。提示词是 Agent 行为的核心"代码"，却常没有代码级别的工程待遇——无版本的提示词变更，无法归因效果变化。

反模式：提示词里嵌随机时间或不稳定上下文（同时破坏 KV Cache 和可复现性）；一次大 Diff 改多处，无法归因。

## 总结

上下文工程的全部要义：**用"模型此刻需要看到什么"裁决一切进出**。进来的信息要有格式纪律和缓存意识，留下的信息要有生命周期管理，大体积信息要渐进披露，而提示词本身要享受代码的待遇。做完这些，同一个模型的表现会有肉眼可见的差别——因为模型一直没有变，变的是它终于能看到该看的东西。
