> **当 AI 大幅降低"写代码"的成本之后，软件工程的瓶颈正在从代码生成转向代码理解、验证、审查和维护。**

因此，我们评价一门编程语言的标准，也可能发生变化。

过去更关心：

**这门语言对人来说好不好写？**

未来可能更关心：

**这门语言是否适合 AI 生成，同时又方便机器验证和人类审查？**

## 1. AI 降低了"难代码"的生产成本

Armin Ronacher 在《Fast and Hard Code》中提出：

过去很多技术之所以没有被广泛使用，并不完全因为它们不好，而是因为**人类学习和实现成本太高**。

例如：

- Rust
- Zig
- eBPF
- 底层网络编程
- DWARF
- 高性能系统代码

以前选择 Python、JavaScript 等语言，一个重要原因是开发效率高。

但 Coding Agent 出现之后，"我本人是否熟悉这门语言"开始变得没那么重要。AI 可以帮助查文档、处理语法、理解 API，甚至完成大部分实现。

于是技术选择可能越来越倾向于：

> **运行性能、内存安全、程序体积等最终产物的质量，而不是人类手写代码的便利程度。**

可以概括为：

**hard code 仍然很 hard，但人类不必亲自承担全部 hard。**

## 2. 写代码越便宜，验证代码越重要

AI 生成代码越多，开发者面对的就越多是：

**"不是我亲手写的代码。"**

因此，类型系统的价值开始上升。

过去类型主要帮助程序员避免错误；现在它还可以成为 **AI 的约束和反馈机制**。

典型循环变成：

**AI 生成代码 → 编译器 / 类型检查器检查 → 返回错误 → AI 修正 → 再检查**

因此，静态类型系统实际上提供了一套 **machine-readable constraints（机器可读约束）**。

但这里真正重要的并不是"静态类型一定胜过动态类型"，而是一个更大的原则：

> **AI 需要能够快速获得客观反馈。**

类型系统只是其中一种反馈机制。

## 3. Elixir 提出了另一个维度：代码是否容易被 AI 理解

José Valim 从 Elixir 出发提出了一套不同的 AI-friendly 特征。

首先是 **immutability（不可变性）**。

不可变数据意味着：

**输入 → 函数 → 新的输出**

数据流更加显式，隐藏状态和远距离副作用更少。

这对于 LLM 很重要，因为模型的 context window 有限。

如果理解一段代码必须追踪几十个对象之间的 mutable state，模型需要读取大量上下文；如果一段代码可以进行 **local reasoning（局部推理）**，AI 更容易正确理解。

因此：

> **对 AI 来说，代码的局部可理解性可能成为一种新的语言优势。**

## 4. 文档和 API 稳定性，也正在成为 AI 基础设施

**生态是否稳定。**

LLM 的训练数据可能同时包含：

- 十年前的教程
- 五年前的 Stack Overflow
- 三年前的博客
- 当前官方文档

如果 API 经常 breaking change：

**旧知识 ≠ 当前现实**

模型就很容易生成已经失效的代码。

反过来，如果语言和标准库长期保持兼容：

**历史训练数据 ≈ 当前正确知识**

那么 AI 生成代码的可靠性天然更高。

所以：

> **API stability 不再只是 developer experience，也开始成为 AI experience。**

高质量、结构统一、可执行的官方文档同样如此。

## 5. 真正重要的是 Feedback Loop

未来 Coding Agent 的工作方式并不是：

**Prompt → 一次性生成正确代码**

而更接近：

**生成 → 编译 → 测试 → 观察错误 → 修改 → 再验证**

因此适合 Agent 的开发环境应该提供大量廉价、快速、确定性的反馈，例如：

- Type checker
- Compiler
- Tests
- Linter
- Fuzz testing
- Benchmark
- Static analysis
- Runtime introspection
- Profiler

核心不是 AI 第一次能不能写对。

而是：

> **AI 写错以后，系统能否迅速告诉它"哪里错了"。**

## 6. 可观察性

Elixir/BEAM 的优势不完全来自类型系统，而来自强大的 runtime introspection。

Agent 不仅可以：

**read source code**

还可能做到：

**运行程序 → 检查进程状态 → 查看 mailbox → 观察真实运行状态 → 修改代码**

于是 AI 获得的不再只是静态代码，而是程序真实行为的反馈。

这提示了一个更大的方向：

> **未来 AI-friendly 的开发环境，不仅应该可验证，还应该可观察。**

## 7. Go 和 Rust 为什么重新受到关注

### Go

Go 的优势是：

**简单、统一、可预测、容易阅读。**

它故意限制语言表达方式，让不同开发者写出来的代码比较相似。

这在过去有时被批评为"无聊"。

但 AI 时代，"无聊"可能反而是一种优势：

**AI 更容易稳定生成，人类更容易快速 review。**

Google 那篇文章进一步从完整软件工程工具链解释了 Go 的优势，这部分可以单独展开。

### Rust

Rust 的优势则是：

**AI 可以承担难写的部分，而编译器负责严格约束。**

过去 Rust 的问题之一是学习和编写成本很高。

但如果代码主要由 AI 生成，人类主要负责 review，那么：

**难写但容易验证**

可能成为一个非常好的属性。

因此 Rust 的复杂度，在 Agent 时代可能不再像过去那样构成巨大劣势。

## 8. 程序员角色正在从 Writer 转向 Reviewer

过去程序员工作的核心动作是：

**Write**

未来越来越可能是：

**Specify → Generate → Read → Review → Verify**

也就是从：

> **Code Writer**

逐渐转向：

> **Code Reader / Reviewer / System Designer**

因此语言选择也会发生变化。

以前：

**"哪门语言让我最快把东西写出来？"**

以后可能变成：

**"当 Agent 给我生成几千行代码时，哪门语言让我最容易知道这些代码是否可靠？"**

## 结论

综合起来，一个真正 **AI-friendly 的编程语言 / 开发环境**，可能需要具备以下特征：

**1. 易于生成**
语法和语言规则相对明确，不存在过多等价但复杂的表达方式。

**2. 易于理解**
数据流清晰，隐藏状态和副作用较少，可以进行局部推理。

**3. 易于约束**
类型、接口、编译器等能够明确告诉 Agent 什么是合法程序。

**4. 易于验证**
测试、静态分析、fuzz、benchmark 等工具可以自动判断代码质量。

**5. 易于获得反馈**
Agent 写错后能够快速得到结构化错误，并进入下一轮修改。

**6. 易于观察**
能够看到真实 runtime state，而不只是阅读源码。

**7. 生态稳定**
旧文档、旧代码和当前 API 尽可能保持一致。

**8. 容易审查**
人类面对大量 AI-generated code 时，可以快速理解它到底在做什么。

## 最值得记住的一句话

我们讨论的不是：

**"AI 时代哪个编程语言会赢？"**

而是：

> **编程语言正在从"为人类手写代码而设计的工具"，逐渐变成"人类与 Agent 共同进行软件工程的接口"。**

因此，未来最重要的语言特征可能不再只是 **expressiveness（表达能力）** 和 **developer productivity（人工开发效率）**，而会越来越包括：

**predictability、verifiability、observability、auditability。**

也就是：

**可预测、可验证、可观察、可审查。**

最终可以把整个趋势压缩成一句：

> **当生成代码越来越便宜，理解和验证代码就越来越昂贵，也越来越重要。**
